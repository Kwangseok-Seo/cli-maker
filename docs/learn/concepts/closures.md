# closures

함수가 **바깥 변수를 붙잡아** 나중까지 기억하는 것. 루프가 데이터 개수만큼 명령을 만들어 내는 M3 의 동력이다.

## 핵심

```go
for _, c := range m.Commands {
    sub := &cobra.Command{
        Run: func(cmd *cobra.Command, args []string) {
            fmt.Println(c.Method, m.BaseURL+c.Path) // c, m 을 붙잡는다
        },
    }
    group.AddCommand(sub)
}
```

클로저가 붙잡는 것은 값이 아니라 **변수(칸) 그 자체**다. 3줄로 확인:

```go
x := 1
f := func() { fmt.Println(x) }
x = 99
f() // 99 — 값 복사라면 1
```

- 그래서 판단 기준은 하나: **붙잡은 칸이 나중에 바뀌는가.** 우리 `m` 은 `Build` 호출마다 한 번 정해지고 그 뒤 안 바뀌니 루프 밖 변수여도 안전하다.
- 함수 본문의 변수는 **호출 시점에** 읽힌다 — 미실행 코드 덩어리를 담아둔 것이라서.

## 루프 변수와 go.mod (Go 1.22 변경점)

같은 소스에서 `go.mod` 의 `go` 줄만 바꿔 실측한 결과:

| `go.mod` | 출력 |
|---|---|
| `go 1.21` | `findByStatus`, `findByStatus` |
| `go 1.26` | `getPetById`, `findByStatus` |

- **~1.21**: 루프 변수는 루프 전체에 **칸 하나** → 클로저들이 같은 칸을 공유 → 루프 종료 후 마지막 값만 남는다.
- **1.22+**: 루프 변수가 **매 반복마다 새 칸**(per-iteration scope) → 클로저마다 다른 칸.
- 이 시맨틱을 고르는 건 설치된 툴체인이 아니라 **`go.mod` 의 언어 버전**이다. 위 실측은 둘 다 같은 1.26 컴파일러로 냈다 → [[go-modules]].

## 겪은 함정

- "`append` 가 `c` 의 값을 저장했겠지"라는 오해 — `append` 가 담은 것은 **미실행 함수 값 하나**뿐이다. 값이 복사됐다면 `go 1.21` 에서도 정답이 나왔을 것.
- 옛 코드 첫 줄의 `c := c` 자기대입은 1.22 이전에 새 칸을 손으로 만들던 관용구다. 지금은 불필요(무해) — 남의 코드에서 보면 "1.22 이전 습관"으로 읽는다.
- 루프 변수는 안전해졌지만 **루프 밖 변수**를 붙잡으면 여전히 공유된다. 안전 여부는 버전이 아니라 "그 칸이 바뀌는가"가 정한다.
