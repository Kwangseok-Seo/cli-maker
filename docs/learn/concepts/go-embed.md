# go-embed

`//go:embed` 지시문. **빌드 시점에 파일 내용을 바이너리 안으로 넣는다.** 실행할 때 그 파일을 찾지 않는다.

## 핵심

```go
import _ "embed"          // 이름을 안 쓰므로 blank import

//go:embed main.go.tmpl
var mainTmplText string
```

- 주석이 아니라 **지시문**이다. `//go:embed` 와 `//` 사이에 공백이 없어야 하고, **변수 선언 바로 위**에 붙어야 한다.
- 대상은 `string`, `[]byte`, 또는 `embed.FS`.
- 파일은 **그 패키지 디렉토리 아래**에 있어야 한다. `../` 로 올라갈 수 없다.
- 패키지 이름을 안 쓰면 `_ "embed"` 로 blank import — 안 그러면 "imported and not used".

## 왜 문자열 리터럴 대신 파일인가

템플릿을 Go 소스 안에 문자열로 박아도 동작은 같다. 파일로 두면 **도구가 그 내용에 닿는다** — 에디터 문법 강조, `git diff`, 그리고 나중에 템플릿만 고친 커밋이 읽힌다.

우리가 [[text-template]] 으로 뽑는 것이 Go 소스라, 이 차이가 특히 크다. 문자열 안에 갇힌 Go 코드는 `gofmt` 도 `go vet` 도 보지 못한다.

## 정말 들어갔는지 확인

repo 밖에서, 템플릿 파일 없이 실행해 봤다:

```
$ ls
cli-maker.exe  github.yaml         ← main.go.tmpl 이 없다

$ ./cli-maker.exe generate github.yaml
// Code generated by cli-maker. DO NOT EDIT.
...                                 ← 그래도 나온다

$ grep -c 'Code generated by cli-maker' cli-maker.exe
2                                   ← 바이너리 안에 문자열이 있다
```

`go run` 이 아니라 **컴파일된 바이너리를 다른 디렉토리로 옮겨** 확인한 것이 요점이다. repo 안에서 돌리면 파일을 읽는 구현과 구별되지 않는다.

## 겪은 함정

- **파싱 시점을 어디에 둘지.** embed 로 얻은 문자열은 *컴파일 타임 상수가 아니라* 런타임 변수다. 그래서 파싱은 여전히 런타임에 일어나고, 패키지 변수 + `template.Must` 로 **시작할 때 한 번**만 하도록 묶었다([[text-template]]).
- **embed 는 검증을 해 주지 않는다.** 파일이 없으면 컴파일 에러가 나지만, 내용이 올바른 템플릿인지·올바른 Go 인지는 아무도 안 본다. 그 판정은 각각 `template.Parse` 와 [[go-ast]] 의 몫이다.
