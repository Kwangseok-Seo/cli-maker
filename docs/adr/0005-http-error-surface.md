# HTTP 4xx/5xx 는 본문을 내보낸 뒤 종료 코드 1 로 알린다

응답 상태가 4xx/5xx 면 **본문을 stdout 으로 그대로 내보낸 뒤** `HTTP <상태>` 에러를 반환해 종료 코드 1 로 끝낸다 — 스크립트가 실패를 감지할 수 있게 하고 사람에게는 stderr 로 이유를 알리기 위해, curl 의 기본 동작(어떤 상태든 exit 0)과 달라 익숙한 유저가 한 번 놀라는 것을 감수한다.

본문이 **항상 stdout** 이라는 것이 이 결정의 구조적 축이다 — 에러 응답에도 API 의 진짜 설명이 담기므로(`couldn't convert 'abc' to type Long`) `| jq` 로 그것을 읽는 경로가 성공/실패 양쪽에서 동일하게 열려 있어야 한다. 그래서 상태 판정은 본문 복사 **뒤에** 온다. 상태 없이 조기 반환하면 유저가 그 설명을 잃는다.

거부한 대안: **exit 0 유지**(curl 기본)는 `cli-maker ... > pet.json` 이 에러 JSON 을 성공으로 저장하게 만든다. **exit 1 만, stderr 없음**은 본문이 빈 에러를 주는 API 에서 왜 실패했는지 단서를 남기지 않는다. 세 정책을 실제 400 응답으로 대조한 출력은 [M4 로그](../learn/milestones/M4.md).

전송 실패(DNS·연결 거부·타임아웃)는 별개 경로다 — 그쪽은 애초에 응답이 없어 `Do` 가 에러를 준다. 4xx/5xx 는 통신으로는 성공이므로 실패로 볼지가 정책이었다.
