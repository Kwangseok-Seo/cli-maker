# 런타임 인터프리터 아키텍처

우리는 API마다 독립 CLI 를 코드 생성하는 대신, 단일 바이너리가 **Manifest 를 런타임에 읽어 명령을 동적 생성**하는 런타임 인터프리터 방식을 택한다 — 학습 곡선과 반복 루프를 얕게 유지하기 위해, "최종 유저에게 설정 없는 독립 바이너리를 배포"하는 능력을 (당분간) 포기하는 비용을 감수한다.

지향점인 mvanhorn/cli-printing-press 는 코드 생성 방식(API마다 Go+Cobra 바이너리를 찍어냄)이라, 이 결정은 맥락 없이는 의외로 보인다 — 그래서 기록한다. 이 프로젝트의 두 번째 목표가 "Go 를 배우는 과정의 실증"이라, text/template·생성물 빌드 오케스트레이션·생성 코드 디버깅이라는 부수 복잡도를 초반에 얹지 않는 편이 학습 밀도에 유리하다는 판단이 결정을 이끌었다.

## Considered options

- **코드 생성 (거부, 당분간)**: printing press 방식. 독립 배포 바이너리·컴파일 타임 검증이 강점이나 첫 Go 프로젝트로는 무겁다. 런타임 방식이 확정하는 도메인 모델(**Manifest**/**Command** struct)은 코드 생성의 입력과 동일하므로, 뒤에 `generate` 서브커맨드로 **얹을** 수 있다 — 버리고 다시 짜는 전환이 아니다.

## Consequences

- 새 API 추가 = **Manifest** 파일 추가, 재컴파일 불필요.
- 모든 명령이 단일 **Executor** 를 공유 → 명령별 커스텀 로직은 (지금은) 표현하기 어렵다. 필요해지면 그때 코드 생성 경로를 연다.
