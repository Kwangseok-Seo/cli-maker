# 마일스톤이 유저 표면을 늘리면 그 자리에서 발행한다

유저가 쓸 것이 늘어난 마일스톤은 그 마일스톤을 닫을 때 새 minor 를 태그한다 — 발행하지 않으면 `go install …@latest` 로 받는 사람에게 그 기능이 존재하지 않고, `clirun` 의 공개 표면이 넓어진 경우에는 기능이 안 오는 정도가 아니라 **`generate` 산출물이 아예 컴파일되지 않기** 때문이며, 대신 기능이 적은 마일스톤에도 버전 번호가 하나씩 소비되는 것을 감수한다.

근거는 실측이다. v0.1.0 은 M9 직후에 달렸고 M10(`--data`)·M11(`import`)·M12a(발견 경로)·M12b(`--version`)가 그 뒤에 왔는데, 그동안 태그가 그대로였다. 그래서 최신 소스로 `generate` 한 CLI 가 `go mod tidy` 로 v0.1.0 을 끌어와 `undefined: clirun.Body`·`undefined: clirun.AddBodyFlag` 로 죽었다 — 본문을 받는 매니페스트를 뽑은 유저 전부가 그랬다. **세 마일스톤 동안 아무 신호도 없었다**: 우리 테스트는 작업 트리의 소스를 보고 유저만 proxy 를 보기 때문에, 이 격차는 repo 안에서 관측되지 않는다. `clirun` 이 공개 façade 라는 ADR-0009 의 결정에는 *"그 표면의 발행 시점이 곧 생성물의 빌드 가능 여부"* 라는 귀결이 딸려 있었고, 그것을 여기서 명시한다.

거부한 대안은 **생성된 `go.mod` 에 `require` 를 박아 버전을 고정하는 것**이다. ADR-0009 가 `go mod tidy` 에 맡긴 이유가 그대로 유효하고 — 생성 시점 버전을 박으면 그 CLI 는 낡은 cli-maker 에 영구히 묶인다 — 무엇보다 **문제가 풀리지 않는다.** 고정하려는 그 버전이 애초에 발행돼 있어야 한다.

발행은 되돌릴 수 없다. 태그를 푸시하면 proxy 가 그 시점 소스를 영구 캐시하고, 태그를 지우고 force push 해도 서빙은 계속된다. `retract` 지시어는 이후 해석에만 영향을 주고 이미 받아 간 사람에게는 소용없다. 그래서 **README 를 먼저 고치고 그 커밋에 태그를 단다** — 태그된 소스 안의 설치 안내가 자기 자신에 대해 참이어야 하고, 순서를 뒤집으면 그 거짓이 영구히 박힌다.

`v1.0.0` 은 아직 내지 않는다. major 2 부터는 모듈 경로에 `/v2` 가 붙어 생성 템플릿과 이미 생성된 CLI 들의 import 경로까지 따라 바뀌므로, `clirun` 표면이 M10·M11 에서 연달아 넓어진 지금 API 안정성을 약속하면 그 비용을 앞당겨 치른다.
